# CopyMigration Switcher （Migration Switch Tool）

既存 C/C++ ソース内の指定箇所を検索し、その箇所を **コンパイルスイッチで囲った形**（新旧コード切替可能な形式）へ自動変換する Windows GUI ツールです。
単純な文字列置換ではなく、**安全な変更 / 変更前後の可視化 / レビュー可能な差分出力 / バックアップによる復旧性 / 作業証跡の管理** を重視して設計しています。

詳細設計書の **Phase 1～2（初期版の全機能）**、**Phase 4（17章 複数ファイル一括処理）**、**Phase 5（スイッチ定義ヘッダの一元管理）**、**Phase 6（AI 連携による変更仕様書 / 検査仕様書の生成）** まで実装済みです。

---

## 1. ビルド方法

### 1.1 MinGW-w64 / MSYS2（推奨）

```bash
# 単体テスト（Windows 実行ファイルを wine で実行する場合は UTF-8 ロケールを指定）
#   LC_ALL=C.UTF-8 wine build/ms_test.exe
#   API の実疎通まで確認する場合: wine build/ms_test.exe --live <APIキーを書いたファイル>

# MSYS2 UCRT64 もしくは mingw-w64 環境
cd MigrationSwitcher
make            # → build/MigrationSwitcher.exe
make clean
```

Linux からクロスコンパイルする場合:

```bash
sudo apt-get install -y mingw-w64
make CROSS=x86_64-w64-mingw32-
```

ソースは Shift_JIS のため、`Makefile` は `-finput-charset=CP932 -fexec-charset=CP932` を指定しています。

### 1.2 CMake（MSVC / MinGW 共通）

**VS2022 で手動プロジェクトを作成した場合の設定**

| 設定箇所 | 設定値 |
|---|---|
| C/C++ → プリプロセッサ → プリプロセッサの定義 | `UNICODE;_UNICODE` |
| C/C++ → コマンド ライン → 追加オプション | `/source-charset:.932 /execution-charset:.932` |
| リンカー → 入力 → 追加の依存ファイル | `comctl32.lib;comdlg32.lib;shlwapi.lib;ole32.lib;shell32.lib;gdi32.lib;user32.lib;advapi32.lib;winhttp.lib` |
| リンカー → システム → サブシステム | `Windows (/SUBSYSTEM:WINDOWS)` |
| リンカー → マニフェスト ファイル → マニフェストの生成 | `いいえ (/MANIFEST:NO)` |
| プロジェクトに含めるファイル | `src\*.cpp` と `src\app.rc` のみ（`test\` は含めない） |

**VS2022 でビルドエラーになる場合の対処**

| エラー | 原因 | 対処 |
|---|---|---|
| `LNK2005: main は既に console_test.obj で定義されています` | `test/` 配下のテスト用ファイルを GUI プロジェクトへ追加している | `test/console_test.cpp` と `test/sample.c` / `test/existing_switch.c` を**プロジェクトから除外**してください（サンプルはツールの入力データで、ビルド対象ではありません）。テストは `test/CMakeLists.txt` で別プロジェクトとしてビルドします |
| `CVT1100: 重複するリソースです type:MANIFEST, name:1` | `app.rc` が埋め込むマニフェストと、リンカーが自動生成するマニフェストが同じ ID 1 で衝突 | リンカー → マニフェスト ファイル → **マニフェストの生成 = いいえ (/MANIFEST:NO)** に設定してください（`CMakeLists.txt` では設定済み）。自動生成を残したい場合は `src/app.rc` の `IDM_APP_MANIFEST 24 "app.manifest"` 行を削除し、代わりに リンカー → マニフェスト ファイル → **追加のマニフェスト ファイル = src\app.manifest** を指定してください |
| `LNK1123: COFF への変換中に障害が発生しました` | 上の `CVT1100` に付随して発生 | マニフェストの設定を直せば解消します |

> 本ソースは `test/` を GUI プロジェクトへ追加しても壊れないよう、テストハーネスを
> `MS_BUILD_CONSOLE_TESTS`、サンプルを `MS_COMPILE_SAMPLES` で囲み、
> 未定義時は空の翻訳単位になるようにしています。



> **ソースファイルの文字コードは Shift_JIS (CP932)、改行は CRLF** です。
> `CMakeLists.txt` は MSVC に `/source-charset:.932 /execution-charset:.932` を指定しているため、
> そのまま `cmake` でビルドできます（VS2022 で手動プロジェクトを作る場合も同じ指定が必要です）。
> リンクには `comdlg32`（ファイルダイアログ）と `winhttp`（AI 連携）が必要です。

```bat
mkdir build && cd build
cmake .. -G "Visual Studio 17 2022" -A x64
cmake --build . --config Release
```

### 1.4 テスト（ms_test.exe）を VS2022 でビルドする

GUI 版とは**別のソリューション**としてビルドします（`test/CMakeLists.txt` を使用）。

**方法A: CMake でソリューションを生成（推奨）**

```bat
cd D:\C++\MigrationSwitcher
cmake -S test -B build_test -G "Visual Studio 17 2022" -A x64
cmake --build build_test --config Release
build_test\Release\ms_test.exe
```

生成された `build_test\MigrationSwitcherTests.sln` を VS2022 で開けば、
ブレークポイントを張ってデバッグ実行できます（スタートアップ プロジェクトは `ms_test`）。

**方法B: VS2022 の「フォルダーを開く」から CMake プロジェクトとして開く**

1. VS2022 → 「ファイル」→「開く」→「**CMake**」→ `D:\C++\MigrationSwitcher\test\CMakeLists.txt` を選択
2. 「構成」ドロップダウンで `x64-Release` を選び、「ビルド」→「すべてビルド」
3. 「スタートアップ項目の選択」で **ms_test.exe** を選び、`Ctrl+F5` で実行

**方法C: 既存の GUI ソリューションに 2 つ目のプロジェクトとして追加する**

1. ソリューションを右クリック →「追加」→「新しいプロジェクト」→「空のプロジェクト」(名前: `ms_test`)
2. プロジェクトのプロパティを設定

| 設定箇所 | 設定値 |
|---|---|
| C/C++ → プリプロセッサ → プリプロセッサの定義 | `UNICODE;_UNICODE;MS_BUILD_CONSOLE_TESTS` |
| C/C++ → コマンド ライン → 追加オプション | `/source-charset:.932 /execution-charset:.932` |
| C/C++ → 全般 → 追加のインクルード ディレクトリ | `..\src` |
| リンカー → 入力 → 追加の依存ファイル | `comctl32.lib;comdlg32.lib;shlwapi.lib;ole32.lib;shell32.lib;gdi32.lib;user32.lib;advapi32.lib;winhttp.lib` |
| リンカー → システム → サブシステム | `コンソール (/SUBSYSTEM:CONSOLE)` |

3. プロジェクトへ次のファイルを追加
   - `src\*.cpp` … **`main.cpp` を除く**すべて（`src\app.rc` は**追加しない**）
   - `test\console_test.cpp` … **`MS_BUILD_CONSOLE_TESTS` の定義が必須**（未定義だと空の翻訳単位になります）

**実行方法**

```
> build_test\Release\ms_test.exe
> build_test\Release\ms_test.exe --live key.txt      （API の実疎通も確認する場合）
```

- `--live` の引数には、**Genspark API キーを 1 行だけ書いたテキストファイル**のパスを指定します（省略時は API を呼びません）。
- テストは `%TEMP%\ms_verify` 配下で作業ファイルを作成・削除します。
- 出力はコンソール（標準出力）に `PASS` / `FAIL` として表示され、最後に合計が出ます。

## 3. 使い方（設計書 2.4 想定利用シーン）

### ケース1: 単一ファイル内の旧コードを切替可能化

1. **対象ファイル** を「参照...」で選択（ドラッグ＆ドロップでも可）
2. **スイッチ名** を入力（例: `MIGRATION_001`）
   - 入力中にバリデーション結果が右側に表示されます
3. 「旧コード」タブに差し替え対象コードを入力（インデント・タブはそのまま保持）
4. 「新コード」タブに新コードを入力
5. 「基本設定」タブで置換方式（A～D）とオプションを選択
6. **検索** → 「検索結果」タブでヒット一覧を確認、置換対象にチェック
7. **プレビュー** → 生成されるコンパイルスイッチと変更前後を確認
8. **実行** → 確認ダイアログ → バックアップ作成 → ファイル更新 → レポート出力

### ケース2: レビュー資料として提出

**ドライラン** を実行すると、検索・検証・プレビュー・HTMLレポート生成のみを行い、ファイルは一切変更しません。出力された HTML をレビュー担当者へ提出し、承認後に本実行します。

### ケース4: スイッチ定義を 1 つのヘッダで一元管理する（Phase 5）

1. 「スイッチ管理」タブで **スイッチ定義ヘッダ**（既定 `migration_switch.h`）の出力先を指定
2. 「スイッチ定義ヘッダを管理する」を ON にすると、実行時に
   **ヘッダの生成・更新** と **対象ソースへの `#include` 自動挿入** をツールが行います
3. 実行後、スイッチ管理タブの一覧に登録されたスイッチが表示されます
   （**有効化 / 無効化 / 削除 / オープン** が可能）
4. 既定はすべて **無効（コメントアウト）** のため、切替はヘッダ 1 行のコメントを外すだけです

---

### ケース5: 変更仕様書・検査仕様書を AI で作成する（Phase 6）

1. 「基本設定」タブの **AI 連携** に **API キー**（Genspark API キー `gsk-...`）を入力し、「接続テスト」で疎通確認
2. 「システム情報」タブに **システム名 / システム概要 / 目的 / 修正箇所概要**（必要なら追加指示）を入力
3. **「変更仕様書を生成」「検査仕様書を生成」「両方を生成」** のいずれかを押す
4. 生成された Markdown が画面下部に表示され、同時に `reports/` へ HTML レポートとして保存されます
   （`<システム名>_changespec_<日時>.html` / `<システム名>_inspectspec_<日時>.html`）

プロンプトには、入力したシステム情報に加えて **スイッチ名・旧コード・新コード・対象ファイル・スイッチ定義ヘッダの内容** が自動で埋め込まれるため、実際の移行内容に即した仕様書になります。

---

### ケース3: 誤操作からの復旧

**元に戻す** を押すと、直前実行時のバックアップからファイルを復元します（初期版は直前 1 回のみ）。

### 安全性
| 機能 | 実装内容 |
|---|---|
| バックアップ作成 | `対象ファイル名.yyyymmdd_hhmmss.bak` を対象と同一フォルダ（または `backups/`）に作成。作成失敗時は実行中断 |

### 検証
スイッチ名バリデーション（先頭英字/_、英数字と_のみ、予約語警告）/ ファイル存在確認 /
読み書き権限確認 / 空入力チェック / ディスク・ロック検出 / システムディレクトリ警告

### 高度検索（初期版の範囲）
複数ヒット選択（チェックボックス＋「すべて選択 / 選択を解除」）/
既存コンパイルスイッチ近傍警告（既定 前後 5 行、`#if #ifdef #ifndef #else #elif #endif`）/
コメント内ヒット警告（`//` および `/* */`、文字列リテラル・文字リテラルは除外する簡易字句判定）

### 利便性
設定保存（`config.ini`：8.1 AppConfig 全項目）/ インデント自動調整（オプション、6.8 仕様準拠）/ テンプレート方式（18章 `${SWITCH} ${OLD_CODE} ${NEW_CODE} ${DATE} ${USER} ${FILE}`）

### 一括処理（Phase 4 / 設計書 17章）

| 機能 | 実装内容 |
|---|---|
| 複数ファイル検索 | フォルダ配下の全対象ファイルを検索し、ヒット一覧へ集約（`BatchProcessor::SearchFolder`） |
| フォルダ指定 | 「一括処理」タブの対象種別でフォルダを選択（ドラッグ＆ドロップにも対応） |
| 拡張子フィルタ | `.c .cpp .h .hpp .cs .java` のチェックボックス＋サブフォルダ有無（`FolderScanner`） |
| ファイル単位の選択 | 対象ファイル一覧のチェックで一括処理の対象を絞り込み（「すべて選択／すべて解除」） |
| 一括プレビュー | ファイルごとの変更前後をまとめて表示（上限 50 ファイル、残りは統合レポートで確認） |
| 一括バックアップ | 書き換え対象の全ファイルを個別にバックアップしてから変換 |
| 一括変換 | ファイルごとの文字コード・改行コード・インデントを維持して一括変換 |
| 統合レポート | 全ファイルを 1 つの HTML にまとめる（サマリ表＋ファイル別の差分・警告） |
| 一括 Undo | 直前の一括操作に含まれる全ファイルをまとめて復元 |

**走査の安全設計**: 上限 20,000 ファイル / 1 ファイル 8MB。シンボリックリンク・ジャンクションは辿りません。
**一括実行の安全設計**: ファイル単位で「検索後に変更されていないか」を再検証し、変更を検出したファイルはスキップします。失敗したファイルがあっても他のファイルの処理は継続し、結果は統合レポートと一覧の「状態」列で確認できます。

### 文字コード・改行（設計書 3.4 / 6.5.3）
| 項目 | 対応 |
|---|---|
| UTF-8 | 対応 |
| UTF-8 BOM 付き | 対応（BOM を維持して書き戻し） |
| Shift_JIS (CP932) | 対応 |
| UTF-16 LE | BOM 付きのみ読込対応（書戻しも可） |

## 6. コンパイルスイッチ変換方式（設計書 6.7）

| 方式 | 出力 |
|---|---|
| A: `#ifdef` 新コード優先 | `#ifdef SW` / 新コード / `#else` / 旧コード / `#endif` |
| B: `#ifndef` 旧コード優先 | `#ifndef SW` / 旧コード / `#else` / 新コード / `#endif` |
| C: コメント付き | `#ifdef SW  /* migration start */` ～ `#endif              /* SW */` |
| D: 開始終了コメント | `/* SW start */` ～ `/* SW end */` で全体を挟む |
| T: テンプレート | `config.ini` の `CustomTemplate` を `${...}` 展開 |

### 6.5 スイッチ定義ヘッダの一元管理（Phase 5）

コンパイルスイッチの `#define` をソース内に散在させず、**1 つのスイッチ定義ヘッダ**へ集約して管理します。

| 項目 | 内容 |
|---|---|
| ヘッダ名 / 出力先 | 既定 `migration_switch.h`（対象ソースと別フォルダなら相対パス、別ドライブなら絶対パスで `#include`） |
| 管理領域 | ヘッダ内の `/* ==== CopyMigration Switcher managed section: BEGIN ==== */` ～ `END` のみを書き換え。**管理領域外（手動定義領域）は書き換えません** |
| スイッチの記述 | スイッチごとに `/* NAME : 説明 */` と `/* #define NAME */`（無効）／`#define NAME`（有効）の 2 行 |
| 既定状態 | **すべて無効**＝旧コード側（安全側）。必要なスイッチだけ有効化します |
| `#include` 挿入位置 | ①最後の `#include` 直後 → ②`#ifndef`/`#define` ガード直後 → ③先頭コメントブロック後 → ④先頭（冪等。既にあれば追加しません） |
| 一括処理との連携 | 対象ファイルごとに `#include` を挿入し、統合レポートにもヘッダ情報・追加行を出力 |
| Undo | 新規作成されたヘッダは「削除して戻す」、既存ヘッダは内容を復元（`UndoRecord::remove_on_undo`） |
| ドライラン | ヘッダ生成・更新・`#include` 追加のいずれも**行いません**（ファイル無変更） |

#### 行中一致の行頭ホイスト（6.7 補足）

`    return old_function(x);` のように一致箇所が**行の途中**にある場合、ブロックをそのまま差し込むと
`#ifdef` が行中に来て C/C++ として不正になります。本ツールはこの場合、
**`#ifdef` / `#else` / `#endif` を行頭へ移し、行の前後のコードを各分岐へ複製**します。

```c
    return old_function(x);      /* 変換前 */

#ifdef MIGRATION_001             /* 変換後 */
    return new_function(x);
#else
    return old_function(x);
#endif
```

同一行に複数の一致箇所がある場合は範囲が重なるためホイストを行いません（安全側）。

#### 動作確認（生成物をそのまま gcc でコンパイル）

```bash
cd ms_verify
gcc -o ms_off sample.c && ./ms_off                 # → 2  （スイッチ無効＝旧コード）
gcc -DMIGRATION_001 -o ms_on sample.c && ./ms_on   # → 3  （スイッチ有効＝新コード）
```

## 6.6 AI 連携（変更仕様書 / 検査仕様書の生成）（Phase 6）

「システム情報」タブの入力内容と、移行対象の情報を基に、AI（Genspark API）で **変更仕様書** と **検査仕様書** を生成します。

| 項目 | 内容 |
|---|---|
| 接続先 | `POST https://www.genspark.ai/api/tool_cli/agent_ask`（`X-Api-Key` ヘッダで認証） |
| 送信内容 | `{"message": "<プロンプト>", "task_type": "super_agent"}`（モデル指定時は `use_model` を付加） |
| 受信 | SSE（Server-Sent Events）。`delta` を逐次連結し、完了イベントの `last_message` を最終本文として採用 |
| API キー | 「基本設定」タブの **AI 連携** で入力（`config.ini` の `[Ai] ApiKey` に保存されます） |
| エンドポイント / モデル / タイムアウト | 同タブで変更可能（既定 `600` 秒、30～3600 秒でクランプ） |
| 出力 | 画面下部に Markdown 表示 + `reports/` へ HTML レポート（UTF-8 BOM 付き・日本語対応） |
| 接続テスト | 「接続テスト」ボタンで API キーとエンドポイントの疎通を確認 |

### プロンプトに埋め込まれる情報

- システム名 / システム概要 / 目的 / 修正箇所概要 / 追加指示
- スイッチ名・旧コード・新コード・対象（ファイル数・ヒット件数）
- スイッチ定義ヘッダの内容（存在する場合は抜粋）

### 生成される章立て

| 変更仕様書 | 検査仕様書 |
|---|---|
| 1. 変更概要 / 2. 変更目的・背景 / 3. 変更対象 / 4. 変更内容（変更前・変更後） / 5. コンパイルスイッチ仕様 / 6. 影響範囲と非影響範囲 / 7. 適用手順 / 8. ロールバック手順 / 9. 未確定事項・確認事項 | 1. 検査目的 / 2. 検査範囲と対象外 / 3. 検査観点一覧 / 4. 正常系テストケース / 5. 異常系・境界値テスト / 6. スイッチ切替の確認項目 / 7. 回帰確認項目 / 8. 実施環境・前提条件 / 9. 合否判定基準 / 10. 証跡 |

### 実疎通の確認結果（wine + WinHTTP 経由）

Windows 実行ファイル（`ms_test.exe --live`）から実際に Genspark API を呼び出し、変更仕様書 **11,198 文字**、検査仕様書の応答を取得して HTML レポート（変更仕様書 24,920 バイト / 検査仕様書 51,460 バイト）を生成できることを確認しています。

### API を使わない運用（AI チャットへ貼り付けるだけで仕様書を作る）

API キーを設定できない環境でも同じ仕様書を作成できます。

1. 「システム情報」タブで入力後、**「プロンプトtxt（変更仕様書）」「（検査仕様書）」「両方のプロンプトtxt」** を押す
2. `reports/` に **AI チャットへそのまま貼れる依頼文 txt** が出力されます
   （`<システム名>_changespec_prompt_<日時>.txt`）
3. その txt の内容を **すべてコピーして AI チャット（ChatGPT / Claude / Gemini など）へ貼り付けて送信**
4. 返ってきた回答を **すべてコピー**し、「システム情報」タブの出力欄に貼り付ける
5. **「この内容を変更仕様書にする / 検査仕様書にする」** を押す → HTML レポートが作成されます

出力される txt には次の内容が含まれます。

| 部分 | 内容 |
|---|---|
| 冒頭 | この txt の使い方（コピー → 貼り付け → 回答を貼り戻す手順） |
| 依頼文 | 「あなたは～です」から始まる役割指示、システム情報、対象コード、**記載する章立て**、**出力の厳守事項**（Markdown のみ / 前置き禁止 / 創作禁止 など） |
| 末尾 | 回答を貼り戻すときのメモ（システム名・スイッチ名・対象・種別・作成日時） |

これにより、**API 経由でも手動貼り付けでも同じ章立て・同じレポート形式**の仕様書が得られます。

### 注意事項

- API キーは `config.ini` に**平文**で保存されます。配布物へ含めないでください。
- 出力欄は編集可能です。AI の回答を貼り付けたあと、そのまま手直ししてからレポート化できます。
- 生成物は AI による**草案**です。内容を確認・修正のうえ、正式な仕様書としてご利用ください（レポートにも同旨の注記を出力します）。
- 生成中は「終了」「実行」等の操作を抑止します（状態は `EXECUTING`）。

### API 種別の切り替え（Genspark API / OpenAI 互換 API）

「基本設定」タブの AI 連携に **API 種別** コンボを用意しています。用途に応じて切り替えてください。

| API 種別 | 認証ヘッダ | リクエスト先 | 応答の解釈 |
|---|---|---|---|
| Genspark API（既定） | `X-Api-Key` | `POST https://www.genspark.ai/api/tool_cli/agent_ask` | SSE（`delta` を連結し、完了時の `last_message` を採用） |
| OpenAI 互換 API | `Authorization: Bearer` | `POST {エンドポイント}/chat/completions` | JSON（`choices[0].message.content`。無ければ `choices[0].text`） |

OpenAI 互換 API が使えるサービスの例:

| サービス | エンドポイント設定例 | モデル例 |
|---|---|---|
| OpenAI（GPT） | `https://api.openai.com/v1` | `gpt-4o-mini` |
| Azure OpenAI | `https://<リソース名>.openai.azure.com/openai/deployments/<デプロイ名>/chat/completions?api-version=2024-06-01` | デプロイ名 |
| OpenRouter / Groq / Together など | 各社が示す `/v1` | 各社のモデル名 |
| Ollama（ローカル） | `http://localhost:11434/v1` | `llama3.1` など |
| LM Studio / 社内プロキシ | 各エンドポイント | 任意 |

- エンドポイントは `/v1` まで指定すれば `/chat/completions` を自動補完します。完全な URL を書いた場合はそのまま使用します（Azure の `api-version` 付き URL も可）。
- モデル名は OpenAI 互換 API では必須です。未入力のまま接続テスト・生成を行うとエラーになります。
- キー・エンドポイント・モデルは **API 種別ごとに別々に保存** します（`config.ini` の `[Ai]` セクション: `Provider` / `ApiKey` / `Endpoint` / `Model` / `OpenAiApiKey` / `OpenAiEndpoint` / `OpenAiModel`）。種別を切り替えても入力値が混ざりません。
#### GitHub Copilot への対応状況

GitHub が公式に提供する Copilot の REST API は、シート管理・利用状況メトリクス・コンテンツ除外・クラウドエージェント管理等の **管理／監視用** です。チャット補完（`/chat/completions` 相当）は提供されていないため、**Copilot を API 種別として直接指定することはできません**。

利用できる経路は次の 3 つです。

| 経路 | 内容 | 本ツールでの設定 |
|---|---|---|
| OpenAI 互換の他サービス | OpenAI / Azure OpenAI（AI Foundry）/ OpenRouter / Groq / Ollama / 社内プロキシ等 | API 種別「OpenAI 互換 API」にエンドポイント・キー・モデルを設定 |
| Copilot を OpenAI 互換に変換する**非公式**プロキシ | 例: `copilot-api` が `POST /v1/chat/completions` を公開。GitHub 非公認で予告なく動作しなくなる可能性あり | プロキシを起動し、エンドポイントに `http://localhost:4141/v1` を設定 |
| Agent tasks REST API（公式・public preview） | Copilot クラウドエージェントにタスクを投げて PR を作らせる API。チャット補完ではないため、本ツールの仕様書生成には使えません | 対象外 |

**注意（非公式プロキシを使う場合）**: GitHub は Copilot の過度な自動／スクリプト利用を禁止しており、濫用検知により警告や一時的な Copilot アクセス停止につながる可能性があります。本ツールは 1 操作 1 リクエストですが、短時間に連続実行するのは避けてください。

**参考（廃止済み）**: GitHub Models は 2026 年 7 月 30 日をもって完全に廃止されました（プレイグラウンド・モデルカタログ・推論 API・BYOK すべて提供終了）。

### 走査・検索・実行で必要な入力

| 操作 | 必須 | 不要 |
|---|---|---|
| 走査 | 対象フォルダ、拡張子フィルタ 1 つ以上 | 旧コード・新コード・スイッチ名 |

## 8. 安全設計（設計書 19章）

- **直接上書きしない**: 一時ファイル（`temp/`）へ書き出し → サイズ検証 → `MoveFileEx(REPLACE_EXISTING | WRITE_THROUGH)` で置換
- **書き込み前バックアップ**: バックアップ失敗時は本実行を中断
- **書き込み後検証**: サイズ一致を確認。不一致なら一時ファイルを破棄
- **復旧処理**: 書き込み失敗時はバックアップから自動復旧を試行
- **読み取り専用属性**: 一時的に解除して書き込み、完了後に属性を復元
- **ログの配慮**: ログには対象行・件数のみを出力し、ソース全文や機密情報は出力しない（レポートにはユーザーが指定した変更前後コードのみ出力）。**AI の API キーはログに出力しません**（画面は `ES_PASSWORD` でマスク表示）
