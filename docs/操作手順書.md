## 1. はじめに

### 1.1 このツールが行うこと

ソース中の旧 API 呼び出しなどを、**削除せずにコンパイルスイッチで切替可能な形に置き換えます**。

```c
/* 変換前 */
int rc = stock_alloc(item, qty);

/* 変換後（方式 A: 新コード優先） */
#ifdef MIGRATION_001
    int rc = new_stock_alloc(item, qty, 0);
#else
    int rc = stock_alloc(item, qty);
#endif
```

旧コードが残るため、**問題発生時にスイッチを切り替えるだけで即座に元の挙動へ戻せます**。移行期間中の安全弁として使うことを目的としています。

### 1.2 安全設計の要点

| 仕組み | 内容 |
|---|---|
| 走査 → 検索 → プレビュー → 実行 の段階分離 | 各段階で内容を確認してから次へ進む |
| ドライラン | ファイルを書き換えずに結果だけ確認できる |
| バックアップ | 書き換え前のファイルを退避（既定で有効） |
| 変更検知 | 検索後にファイルが変更されていたら、安全のため自動的に中断する |
| 元に戻す | 直前の実行を取り消せる |
| 警告 | コメント内の一致、既存 `#ifdef` の近傍を検出して警告する |

## 3. ビルドと起動

### 3.1 MinGW-w64 / MSYS2

```bash
make                 # GUI 版 build/MigrationSwitcher.exe
make build/ms_test.exe   # 単体テスト
```

### 3.2 Visual Studio 2022

1. 新規プロジェクト（Windows デスクトップアプリケーション / C++）を作成
2. プロジェクトに **`src\*.cpp` と `src\app.rc` のみ** を追加（`test\` は追加しない）
3. プロパティを設定

| 設定項目 | 値 |
|---|---|
| 構成の種類 | アプリケーション (.exe) |
| サブシステム | Windows (/SUBSYSTEM:WINDOWS) |
| 文字セット | Unicode |
| C/C++ → 詳細 → ソース文字セットの強制 | `/source-charset:.932` |
| C/C++ → 詳細 → 実行文字セットの強制 | `/execution-charset:.932` |
| リンカー → 入力 → 追加の依存ファイル | `comctl32;comdlg32;shlwapi;ole32;shell32;gdi32;user32;advapi32;winhttp` |
| マニフェスト ツール → 入力と出力 → マニフェストの生成 | いいえ (/MANIFEST:NO) |
| プリプロセッサの定義 | `UNICODE;_UNICODE` |

### 3.3 バッチファイルでのビルド（推奨）

リポジトリ直下の `build.bat` を使うと、ツールチェーンを自動判定してビルドできます。

```bat
build.bat            rem 自動判定してビルド
build.bat test       rem 単体テストをビルドして実行
build.bat clean      rem build\ を削除
run.bat              rem 実行ファイルを起動
```

| ツールチェーン | 出力 |
|---|---|
| Visual Studio 2022 | `build\Release\MigrationSwitcher.exe` |
| MinGW-w64 / MSYS2 | `build\MigrationSwitcher.exe` |

Visual Studio が見つからない場合は、Visual Studio Installer で「C++ によるデスクトップ開発」をインストールしてください。MinGW-w64 の場合は MSYS2 の UCRT64 シェルで `pacman -S mingw-w64-ucrt-x86_64-gcc make` を実行します。

> バッチファイルは **Shift_JIS (CP932) / CRLF** です。cmd.exe が CP932 を前提とするため作業ツリーは CP932 のままですが、`.gitattributes` の `working-tree-encoding=CP932` により**リポジトリ（GitHub）には UTF-8 で格納**されるため、GitHub 上で文字化けしません。

### 3.4 起動

`build\MigrationSwitcher.exe` を実行します。インストーラは不要で、レジストリも使いません。設定は実行ファイルと同じフォルダの `config.ini` に保存されます。

## 4. 作業フロー全体像

```
[基本設定] 方式・オプションを決める
     ↓
[対象指定] 単一ファイル または フォルダ + 拡張子フィルタ
     ↓
[走査]     ← フォルダモードのみ。新旧コードは不要
     ↓
[旧コード/新コード] 入力
     ↓
[検索]     ← 旧コードだけで実行可
     ↓
[検索結果] 対象にチェック（警告を確認）
     ↓
[プレビュー] 変換後の姿を確認
     ↓
[ドライラン] 書き換えずに結果確認
     ↓
[実行]     バックアップ + 書き換え + レポート
     ↓
[元に戻す] 問題があれば取り消し
```

> **ポイント**: どの段階でも、必須項目が欠けていると次へ進めません。逆に言えば、必須項目を満たせば「走査」は新旧コード未入力でも実行できます。

## 5. 手順 1: 基本設定

「基本設定」タブで、置換方式とオプションを決めます。ここでの設定は実行時の挙動に直結します。

### 5.1 置換方式（必須）

| 方式 | 生成される形 | 使いどころ |
|---|---|---|
| **方式 A: 新コード優先** | `#ifdef スイッチ` / 新コード / `#else` / 旧コード / `#endif` | **通常はこれ**。移行済みコードを既定にし、スイッチ未定義時のみ旧コードへ戻す |
| **方式 B: 旧コード優先** | `#ifndef スイッチ` / 旧コード / `#else` / 新コード / `#endif` | 既定は旧挙動のままにし、明示的にスイッチを定義したときだけ新コードを使う |
| **方式 C: コメント付き方式** | 各分岐にコメントを付与 | レビューで差分を追いやすくしたい場合 |
| **方式 D: 開始終了コメント方式** | `/* MIGRATION_001 BEGIN */` 〜 `/* MIGRATION_001 END */` | 後から機械的に再検出・再変換したい場合 |

> 方式 A と B は**スイッチを定義したときの挙動が逆**になります。移行計画（既定をどちらにするか）に合わせて選んでください。

### 5.2 オプション

| オプション | 既定 | 説明 |
|---|---|---|
| バックアップを作成する | 有効 | 書き換え前のファイルを退避する。**無効化は非推奨** |
| HTML差分レポートを出力する | 有効 | 変換前後の差分を HTML で出力する |
| 実行ログを出力する | 有効 | 実行ログをファイルに残す |
| 実行後にレポートを開く | 有効 | 実行完了後にレポートを既定ブラウザで開く |
| ドライランのみ（実行を抑止） | 無効 | 有効にすると「実行」ボタンでも書き換えを行わない |
| インデントを自動調整する | 有効 | 元の行のインデントに合わせて生成コードを整形する |
| コメント内の一致を警告する | 有効 | コメント内のヒットを警告表示する（コメント内のコードは実行されないため） |
| 既存コンパイルスイッチ近傍を警告する | 有効 | 既存の `#ifdef` / `#ifndef` / `#else` / `#endif` の近く、またはその**内側**にあるヒットを警告する（二重ネスト防止）。**include guard**（`#ifndef G` / `#define G` … `#endif` でファイル全体を包む形）は移行スイッチではないため除外します |

### 5.3 ヒット時の動作

| 設定 | 説明 |
|---|---|
| 1 件の場合のみ自動選択 | ヒットが 1 件のときだけ自動で置換対象にする（**既定・推奨**） |
| 最初の 1 件を対象にする | 各ファイルの最初のヒットだけを対象にする |
| すべての一致を対象にする | 全ヒットを対象にする（**内容を必ず確認してから**） |
| ユーザーが一覧から選択する | 自動選択せず、常に手動で選ぶ |

### 5.4 AI 連携（後述）

「AI 連携」グループの設定は [17 章](#17-ai-連携変更仕様書--検査仕様書の生成) で説明します。使わない場合は空のままで構いません。

## 6. 手順 2: 対象の指定と走査

### 6.1 単一ファイルを変換する場合

1. 「対象種別」で **単一ファイル** を選ぶ
2. 「参照...」で対象ファイルを選択する
3. → [手順 3](#7-手順-3-旧コード新コードの入力) へ進む（走査は不要）

### 6.2 フォルダ内を一括変換する場合

1. 「対象種別」で **フォルダ** を選ぶ
2. 「対象フォルダ」の「参照...」でフォルダを選択する
3. 「拡張子フィルタ」で対象拡張子にチェックを入れる（`.c` / `.cpp` / `.h` など）
4. 必要に応じて **サブフォルダを含める** を有効にする
5. **走査** ボタンを押す

> **重要**: 走査に必要なのは「対象フォルダ」と「拡張子フィルタ」だけです。**旧コード・新コード・スイッチ名は未入力でも走査できます**（走査ボタンは常に押せます）。

走査が完了すると、対象ファイル数がステータスバーとメッセージで通知されます。

```
走査完了: 4 ファイル（新旧コードは未入力でも走査できます）。
次に旧コード・新コードを入力して「検索」を押してください。
```

対象が 0 件のときは警告が出ます。フォルダと拡張子フィルタを見直してください。

> 走査で扱えるファイル数には上限があります（既定 50 件。`FolderScanner::kMaxFiles`）。上限に達すると警告が表示されます。大規模な移行では、対象をサブフォルダ単位に分割して実行してください。

## 7. 手順 3: 旧コード・新コードの入力

| タブ | 入力内容 | 例 |
|---|---|---|
| **旧コード** | 置き換えたい既存のコード | `stock_alloc(item, qty)` |
| **新コード** | 置き換え後のコード | `new_stock_alloc(item, qty, 0)` |

**入力のコツ**

- 前後の空白やインデントは自動で扱われます。行全体をコピーしても構いません。
- 末尾の改行は自動的に除去して検索します。
- 行の途中に現れる旧コードも検出し、必要に応じて行頭へ移動（ホイスト）して `#ifdef` を組み立てます。
- 複数行にまたがる置換は対象外です（[付録 C](#付録-c-既知の制限) 参照）。

**スイッチ名**（基本設定タブ）も入力します。例: `MIGRATION_001`

- **検索時**: 未入力でも警告のみで実行できます
- **実行時**: 必須です（未入力だと実行できません）

---

## 8. 手順 4: 検索

1. **検索** ボタンを押す
2. 結果が「検索結果」タブに一覧表示される

検索は**旧コードだけで実行できます**（新コードとスイッチ名はこの段階では不要です）。検索結果は次のように通知されます。

```
対象コードが 4 件見つかりました。置換対象を選択してください。
```

見つからない場合は、旧コードの表記ゆれ（全角/半角、空白の数）を確認してください。

## 9. 手順 5: 検索結果の確認と対象選択

「検索結果」タブで、置換してよいものだけを選びます。

| 列 | 内容 |
|---|---|
| ファイル名 | ヒットしたファイル |
| ヒット | そのファイル内のヒット件数 |
| 置換対象 | 対象にするか（チェック） |
| 状態 | 対象 / 除外 / 警告 / エラー |
| 行番号 / 列番号 | ヒット位置 |
| 一致種別 / 一致率 | 一致の種類と度合い |

**操作ボタン**

- **すべて選択** — 全ファイルを対象にする
- **すべて解除** — 全ファイルを対象外にする
- **選択を解除** — 選択行の対象を解除する

**必ず確認すべき警告**

| 警告 | 意味 | 対処 |
|---|---|---|
| コメント内の一致 | コメントアウトされたコードへのヒット | 通常は除外する |
| 既存コンパイルスイッチ（内側） | 既存の `#ifdef` 〜 `#endif` の**内側**へのヒット | ネストが二重にならないか確認する |
| 既存コンパイルスイッチ（近傍） | 既存の条件指令の前後 5 行以内へのヒット | 同上（include guard は警告対象外） |

> 状態が「警告」の行は自動では対象になりません。内容を確認したうえで、意図したものだけチェックを入れてください。

## 10. 手順 6: プレビュー

「プレビュー」タブで変換後の姿を確認します。表示モードを切り替えられます。

| モード | 説明 |
|---|---|
| 前後比較表示 | 変換前と変換後を上下に並べる |
| 単純表示 | 変換後のコードだけを表示 |
| 左右比較表示 | 変換前と変換後を左右に並べる |
| HTML 表示（ブラウザで開く） | HTML 差分レポートとしてブラウザで開く |

「HTMLレポートを開く」ボタンでもブラウザ表示できます。

**確認ポイント**

- `#ifdef` / `#else` / `#endif` が正しい位置に入っているか
- インデントが崩れていないか
- 行中一致が行頭へ移動され、意味が変わっていないか
- 二重にスイッチが付いていないか

## 11. 手順 7: ドライラン

**ドライラン** ボタンを押すと、**ファイルを一切書き換えずに**結果だけを確認できます。

```
ドライランが完了しました。ファイルは変更されていません。
対象ファイル : 4 件
対象ファイル : 4 件 / 置換件数 : 7 件
```

初回は必ずドライランで件数とレポートを確認してください。基本設定の「ドライランのみ（実行を抑止）」を有効にしておくと、誤って実行してしまう事故を防げます。

---

## 12. 手順 8: 実行

1. 対象件数とプレビュー内容を最終確認する
2. **実行** ボタンを押す
3. 確認ダイアログで内容を確認して OK

```
対象ファイルを書き換えます。よろしいですか？

対象フォルダ : C:\work\src
対象ファイル : 4 件 / 置換件数 : 7 件
```

**実行時に内部で行われること**

1. バックアップの作成（有効時）
2. 変換後テキストの生成
3. 一時ファイルへ書き込み → 原子的に置換（同一ドライブ外でも `CopyFile` + 削除へフォールバックして動作）
4. HTML 差分レポートの出力
5. 実行ログの出力

> 検索後にファイルが外部で変更されていた場合、**安全のため処理は中断**されます。その場合は再検索してください。

---

## 13. 手順 9: 結果確認とレポート

実行後、結果が通知されます。

```
一括処理が完了しました。
成功: 4 件 / 失敗: 0 件 / スキップ: 0 件
置換件数: 7 件
```

失敗がある場合は「状態」列と統合レポートを確認してください。出力物は次のとおりです。

| 出力物 | 内容 |
|---|---|
| HTML 差分レポート | 変換前後の差分（統合レポート） |
| 実行ログ | 実行日時、対象、件数、エラー内容 |

**推奨**: 変換後のソースをビルドして、スイッチ ON / OFF の両方で動作確認してください。

```bash
# スイッチ未定義 → 旧コードが有効
gcc -c target.c

# スイッチ定義 → 新コードが有効
gcc -c -DMIGRATION_001 target.c
```

## 14. 手順 10: 元に戻す（Undo）

直前の実行を取り消すには **元に戻す** ボタンを押します。

```
MS010: Undo が完了しました。
```

- バックアップから復元します
- スイッチ定義ヘッダの更新も取り消されます
- 複数のレコードをまとめて戻せます

> Undo は**直前の 1 回**が対象です。世代をさかのぼる複数世代 Undo は未実装です（[付録 C](#付録-c-既知の制限)）。大きな変更の前には、リポジトリ側でコミットしておくことを推奨します。

## 15. フォルダ一括処理

フォルダモードでは「一括処理」タブが有効になります。

| 手順 | 操作 |
|---|---|
| 1 | 「対象フォルダ」「拡張子フィルタ」「サブフォルダを含める」を指定 |
| 2 | **走査** を押して対象ファイルを確定 |
| 3 | 旧コード・新コード・スイッチ名を入力 |
| 4 | **検索** を押して全ファイルを検索 |
| 5 | 一覧で対象／対象外を調整（すべて選択 / すべて解除 / 選択を解除） |
| 6 | **プレビュー** で確認 |
| 7 | **ドライラン** → **実行** |

「一括処理」タブの一覧には、ファイルごとにヒット件数・対象件数・状態（成功 / 失敗 / スキップ）が表示されます。スイッチ定義ヘッダの `#include` 追加が必要な場合は、ファイルごとに重複しないよう自動で挿入されます。

## 16. スイッチ定義ヘッダの一元管理

スイッチが増えると、`#ifdef` の管理が煩雑になります。「スイッチ管理」タブでは、**スイッチ定義を 1 つのヘッダファイルに集約**できます。

### 16.1 生成されるヘッダ（例）

```c
/* migration_switch.h - 自動生成 */
#ifndef MIGRATION_SWITCH_H
#define MIGRATION_SWITCH_H

/* 在庫引当の新 API へ移行 */
#define MIGRATION_001

#endif /* MIGRATION_SWITCH_H */
```

### 16.2 手順

1. 「スイッチ定義ヘッダ」の「参照...」で既存ヘッダを選ぶ、または「ヘッダファイル名」に新規名（例: `migration_switch.h`）を入力
2. 「出力先フォルダ」を指定
3. 「スイッチの説明」を入力
4. 必要なら **自動化オプション** で「対象ファイルへ `#include` を追加する（重複追加はしません）」を有効にする
5. **ヘッダを今すぐ生成/更新** を押す

### 16.3 スイッチの有効化・無効化

一覧でスイッチを選び、次のボタンで操作します。

| ボタン | 動作 |
|---|---|
| 有効化 | そのスイッチを `#define` する（新コードが有効になる） |
| 無効化 | `#define` をコメントアウトする（旧コードが有効になる） |
| 選択を削除 | スイッチの登録自体を削除する |
| ヘッダを開く | 生成されたヘッダを開いて確認する |
| 読込 | 既存ヘッダを読み込んで一覧に反映する |

一覧の列は「スイッチ名 / 登録元 / 説明 / 更新」です。

> **移行を切り戻すときは「無効化」** を押すだけです。ソースを再編集する必要はありません。

## 16.4 検索条件の絞り込み（類似一致 / 指定行範囲 / 関数単位）

「検索条件」タブで検索の絞り込みを設定します。

### 類似一致検索

表記の揺れ（空白の数など）を許容して検出します。

1. 「類似一致検索を有効にする」にチェック
2. 「一致率のしきい値(%)」を入力（既定 70）

```
完全一致:    int rc = stock_alloc(item, qty);
類似一致:    int rc = stock_alloc(item,  qty);   ← 空白が 2 つでも検出
```

- 一致率は**2 文字組の Dice 係数**で計算します（100% が完全一致）
- 類似一致の結果は**警告状態**になり、置換対象へ自動選択されません。内容を確認して手動で選択してください
- 複数行にまたがるパターンは類似一致の対象外です（完全一致のみ）

### 指定行範囲検索

1. 「指定した行範囲だけを検索する」にチェック
2. 「開始行」「終了行」を入力（**終了行 0 = 最終行まで**）

### 関数単位検索

1. 「指定した関数の本体（{ } の中）だけを検索する」にチェック
2. 「関数名」を入力（例: `stock_use`）

関数本体は括弧の対応を取って検出します。文字列・文字リテラル・コメントは考慮されますが、プリプロセッサは評価しません。指定した関数が見つからないファイルはヒット 0 件として扱われます。

> 指定行範囲と関数単位を同時に有効にした場合は、**両方の範囲が重なる部分**が検索対象になります。

### 文字コードの選択

「文字コード」で読み書きの文字コードを指定します。

| 設定 | 内容 |
|---|---|
| 自動判定 | BOM と内容から判定（既定） |
| UTF-8 / UTF-8 (BOM) / Shift_JIS / **EUC-JP** | 強制指定 |

> 自動判定は CP932 を優先します。EUC-JP のファイルは CP932 としても妥当なバイト列になり得るため、**確実に扱うには「EUC-JP」を明示的に選んでください**。

1. 「検索条件」タブの「WinMergeU.exe のパス」を「参照...」で指定（**初回のみ**）
2. 「プレビュー」タブの **WinMerge で比較（選択した全ファイルをファイルごとに開きます）** を押す

## 16.8 複数世代 Undo

**元に戻す** は直近の操作だけでなく、さかのぼって複数回実行できます。

1. **元に戻す** を押す
2. 確認ダイアログに「Undo 履歴: N 世代」と表示される
3. OK すると 1 世代戻る。**元に戻す** を再度押すと 1 つ前の世代へ戻れる

保持する世代数は「検索条件」タブの「保持する操作世代数」で指定します（1〜100、既定 10）。上限を超えると古い世代から破棄されます。

> 各世代の復元時、現在の内容は `<ファイル名>.<日時>_<連番>.undobak` として退避されます。

### 16.9 既存スイッチ警告の判定ルール

「既存コンパイルスイッチ近傍を警告する」が ON のとき、次の 2 段階で判定します。

| 判定 | 条件 | メッセージ例 |
|---|---|---|
| **内側**（優先） | 対象行が既存の条件ブロック（`#ifdef` 〜 `#endif`）の内側にある | `6 行目の #ifdef LEGACY_MODE の内側です。` |
| **近傍** | 対象行の前後（既定 5 行）に条件指令がある | `9 行目の #endif が対象行の近傍にあります。` |

**include guard は除外します。** `#ifndef SAMPLE_C` / `#define SAMPLE_C` … `#endif /* SAMPLE_C */` のようにファイル全体を包む形は移行スイッチではないため、警告対象から外します。これがないと、ファイル末尾付近の一致がすべて誤って警告になります。`#if !defined(NAME)` 形式も除外します。

**走査行数**（既定 5）を 0 にすると、近傍判定を止めて**内側判定のみ**になります。

## 17. AI 連携（変更仕様書 / 検査仕様書の生成）

「システム情報」タブでは、変換内容から**変更仕様書**と**検査仕様書**を AI で生成できます。

### 17.1 前提: システム情報の入力

| 項目 | 内容 |
|---|---|
| システム名 | 対象システムの名称（**必須**） |
| システム概要 | 何をするシステムか |
| 目的 | 今回の移行の目的 |
| 修正箇所概要 | 変更内容の要約 |
| 追加指示（任意） | AI への補足指示 |

### 17.2 API 種別の選択（重要）

「基本設定」タブの AI 連携で **API 種別** を選びます。

| API 種別 | 認証 | 用途 |
|---|---|---|
| **Genspark API（既定）** | `X-Api-Key` | 既定のクラウド API |
| **OpenAI 互換 API（GPT / Azure / Ollama 等）** | `Authorization: Bearer` | OpenAI、Azure OpenAI、OpenRouter、Groq、Ollama、LM Studio、社内プロキシ等 |

**設定項目**

| 項目 | 説明 |
|---|---|
| API キー | 各サービスのキー（OpenAI なら `sk-...`） |
| エンドポイント | OpenAI 互換なら `https://api.openai.com/v1` のように `/v1` まで指定（`/chat/completions` は自動補完されます） |
| モデル | OpenAI 互換では**必須**（例: `gpt-4o-mini`） |
| タイムアウト(秒) | 既定 600 |
| **接続テスト** | 疎通確認ボタン。成功すると「AI 接続テスト: 成功」と表示 |

**API 種別ごとに設定は別々に保存されます。** 切り替えても入力値が混ざりません。

**エンドポイントの書き方**

| サービス | 記入例 |
|---|---|
| OpenAI | `https://api.openai.com/v1` |
| Azure OpenAI | `https://<リソース名>.openai.azure.com/openai/deployments/<デプロイ名>/chat/completions?api-version=2024-06-01` |
| Ollama（ローカル） | `http://localhost:11434/v1` |
| 社内プロキシ | 提供された `/v1` エンドポイント |

> **GitHub Copilot について**: GitHub が公式に提供する Copilot の REST API はシート管理・利用状況メトリクス等の**管理用**で、チャット補完は提供されていません。そのため Copilot を直接 API 種別として指定することはできません。Copilot を OpenAI 互換に変換する**非公式プロキシ**を経由すれば、本ツールの「OpenAI 互換 API」で利用できますが、GitHub は Copilot の過度な自動利用を禁止しているため、連続実行は避けてください。業務利用では OpenAI / Azure OpenAI の公式キーを推奨します。

### 17.3 仕様書を生成する

1. システム情報を入力する
2. 「変更仕様書を生成」/「検査仕様書を生成」/「両方を生成」のいずれかを押す
3. 「生成後にレポートを開く」が有効なら、完了後にブラウザで開く
4. 「レポートを開く」で後から再表示できる

### 17.4 API を使わずに仕様書を作る（プロンプト txt 方式）

API キーを用意できない場合でも、**AI チャットに貼り付けるだけで**仕様書を作れます。

1. **プロンプトtxt（変更仕様書）** / **プロンプトtxt（検査仕様書）** / **両方のプロンプトtxt** のいずれかを押す
2. 出力された txt ファイルを開き、内容をすべてコピーする
3. 任意の AI チャット（社内 ChatGPT、Copilot など）に貼り付けて送信する
4. 返ってきた回答をコピーする
5. 「出力（AI の生成結果 / AI チャットの回答をここに貼り付け）」欄に貼り付ける
6. **この内容を変更仕様書にする** / **この内容を検査仕様書にする** を押す → レポートとして出力される

生成される txt は「使い方」「依頼文」「貼り戻しメモ」の 3 部構成です。

### 17.5 生成されるレポートの章立て（概要）

- 変更仕様書: 変更の目的、対象範囲、変更前後の対応、スイッチ一覧、影響範囲、切り戻し手順
- 検査仕様書: 検査方針、検査項目、確認手順、スイッチ別の確認観点、回帰確認のポイント

## 19. トラブルシューティング

| 症状 | 原因 | 対処 |
|---|---|---|
| 走査ボタンが押せない | フォルダモードになっていない | 「対象種別」で **フォルダ** を選ぶ |
| 走査してもファイルが 0 件 | フォルダ未指定 / 拡張子未選択 / 対象がサブフォルダのみ | フォルダと拡張子フィルタを確認。必要なら「サブフォルダを含める」を有効化 |
| 走査で「上限に達しました」と出る | 対象ファイル数が上限（50 件）を超えた | 対象フォルダを分割して実行する |
| 検索で 0 件 | 旧コードの表記が実ソースと一致していない | 実際のソースからコピーし直す。空白・全角半角を確認 |
| 検索で「スイッチ名を入力してください」と出る | スイッチ名未入力（実行時は必須） | 基本設定タブでスイッチ名を入力（検索時は警告のみで続行可） |
| 実行できない | 必須項目の不足 | 旧コード・スイッチ名・対象選択を確認 |
| 「対象ファイルが検索後に変更されています」と出る | 検索後に外部でファイルが変更された | 再検索してから実行する |
| 書き込みに失敗する | 権限不足 / ファイルが他プロセスで使用中 / 読み取り専用属性 | エディタやビルドツールを閉じ、属性と権限を確認。失敗時は自動でバックアップから復旧します |
| 別ドライブへ出力できない | ドライブをまたぐ移動の制約 | 本ツールは自動的にコピー + 削除へフォールバックします。それでも失敗する場合は出力先を同一ドライブにする |
| AI 連携で「API キーが未設定です」と出る | キー未入力 | 基本設定タブの AI 連携でキーを入力する |
| AI 連携でエラーになる（OpenAI 互換） | モデル名未入力 / エンドポイント誤り / キー誤り | 「接続テスト」で切り分ける。エラーメッセージの HTTP ステータスと本文を確認する |
| AI が日本語で返さない | モデルやプロンプトの言語指定 | プロンプト txt 方式を使い、依頼文に「日本語で出力」と追記する |
| 類似一致が検出されない | しきい値が高い / 複数行のパターン | しきい値を下げる。複数行は完全一致のみ対応 |
| 類似一致が置換対象にならない | 仕様（警告状態のため） | 検索結果タブで内容を確認し、手動でチェックを入れる |
| 関数単位検索でヒットしない | 関数名の誤り | 引数リスト直前の識別子を指定する（例: `stock_use`） |
| EUC-JP のファイルが文字化けする | 自動判定が CP932 を優先した | 「文字コード」で **EUC-JP** を明示選択する |
| WinMerge が起動しない | パス未設定 / 未インストール | 「検索条件」タブで `WinMergeU.exe` のパスを指定する |
| 変換後のコードでビルドエラー | スイッチ定義ヘッダが `#include` されていない | スイッチ管理タブの「対象ファイルへ #include を追加する」を有効にして再実行、または手動で `#include` を追加 |
| コメント内のコードまで置換されそうになる | コメント内ヒット | 検索結果タブで該当行を対象外にする（既定で警告表示されます） |

## 付録 A: GitHub への公開手順

### A.1 事前準備

1. Git をインストール（`git --version` で確認）
2. GitHub でリポジトリを作成（Public / Private を選択。**社内資産なら Private を推奨**）
3. コミット者情報を設定

```bash
git config --global user.name  "Your Name"
git config --global user.email "you@example.com"
```

### A.2 `.gitignore` を作成する（必須）

ビルド生成物と**秘密情報を含む設定ファイル**を除外します。

```gitignore
# ビルド生成物
build/
*.o
*.obj
*.exe
*.pdb
*.ilk

# 実行時生成物
config.ini
*.log
reports/
backups/
*.bak
*.undobak

# エディタ / OS
.vs/
.vscode/
*.user
Thumbs.db
desktop.ini
```

> **最重要**: `config.ini` には API キーが平文で入ります。**絶対にコミットしないでください。**
> もし誤ってコミットした場合は、キーを失効させて再発行したうえで、履歴から削除してください（履歴に残ったキーは漏洩したものとして扱います）。

### A.3 `.gitattributes` を作成する（文字コード・改行の保護）

ソースは **UTF-8（BOM 付き）+ CRLF** を前提としているため、Git の自動改行変換を無効化します。

```gitattributes
# ソースの改行コードを変換しない（UTF-8 + CRLF を維持）
* -text
```

> この設定がないと、環境によって CRLF が LF に変換され、`-finput-charset=UTF-8` 前提のビルドやリソースファイルの解釈に影響する可能性があります。

### A.4 Markdown は UTF-8 に変換する（重要）

**文字コードはすべて UTF-8 で統一されています。**

| 対象 | 作業ツリー | リポジトリ（GitHub） |
|---|---|---|
| `src/*.cpp` / `*.h` / `*.rc`、`test/console_test.cpp` | UTF-8（BOM 付き） | UTF-8 |
| `Makefile` / `CMakeLists.txt` | UTF-8（BOM なし） | UTF-8 |
| `*.bat` | Shift_JIS (CP932) | UTF-8（`working-tree-encoding=CP932` で変換） |
| `README.md` / `docs/*.md` | UTF-8（LF） | UTF-8 |

`*.bat` だけ作業ツリーを CP932 のままにしているのは、cmd.exe が UTF-8 (BOM 付き) の
バッチファイルを解釈できず、また `chcp 65001` にすると MSVC の日本語メッセージが
化けるためです。Git 側で UTF-8 に変換して格納するので、GitHub 上では正しく表示されます。

確認方法:

```bash
git check-attr working-tree-encoding -- build.bat     # -> working-tree-encoding: CP932
git show HEAD:build.bat | head -3                     # -> UTF-8 で表示される
```

> なお **`src/` 配下のソースも UTF-8** です。ビルド設定（`-finput-charset=UTF-8` /
> `/source-charset:utf-8`）は UTF-8 前提になっているため、**CP932 へ戻さないでください**。

### A.5 コミットして push する

```bash
cd MigrationSwitcher
git init
git add .
```

## 付録: EUC-JP の扱い

EUC-JP の判定・変換は内蔵テーブル（JIS X 0208 / JIS X 0212、`src/EucJpTable.cpp`）で行います。コードページ 51932 は kernel32 に存在せず（`IsValidCodePage` が 0、`MultiByteToWideChar` は `ERROR_INVALID_PARAMETER` で失敗）、OS のコードページに依存すると実機で EUC-JP を判定できないためです。
